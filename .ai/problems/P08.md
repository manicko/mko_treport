## 1. Problem statement / required behavior (clarified)

For template insertion with `insert_rows=TRUE`, do **not** delete template rows and do **not** shrink the copied/inserted snapshot range. Instead adjust placement/preparation so that:
- **Sample row `P` (`paste_row`) is inserted `H-2` times** (where `H = snapshot.Rows.Count`, after any `skip_header` slicing per current behavior).
- **Snapshot copy/paste is performed to cell `(P-1, paste_col)`** (one row above configured `paste_row`), over full snapshot size `H x W`.

Intent (as clarified): cover/use the template rows immediately above and below the originally targeted inserted area without row deletion and without reducing snapshot data.

## 2. Current behavior and root cause (code check)

**Evidence:** `mko_treport/src/vbs/export/modTreportExtract.bas`
- `CopyPivotSnapshot` (`:16-105`) implements P05/P07 flow:
  - `H = srcRg.Rows.Count`, `W = srcRg.Columns.Count` from presented (optionally `skip_header`-sliced) range (`:43-80`).
  - If `insertRows And H > 1`: copies entire sample row `P` and inserts **`H-1`** copies starting at `P` → prepared space `P..P+H-1` (`:82-89`). `H=1` => no row insertions.
  - Writes snapshot at **`(P, pc)`** over `H x W` (`:91-92`).
  - Returns range **`P..P+H-1`** (`:94`). No deletions (`:17-19`, `:141`).
- `PasteSnapshotData` (`:107-139`) handles `only_values` transfer only; no row prep/deletion.
- `modTreportRun.bas:200-212`: normalizes `pr/pc` (clamps to `>=1`), calls `CopyPivotSnapshot(..., pr, pc, ...)`, then applies formatting/grouping to returned range.

**Root cause of reported template-boundary issue:** current P05 logic uses `H-1` inserts at `P` and pastes at `P`, so it neither deletes nor repositions to include template rows above/below the target area as now requested. Behavior matches P05/005 spec and docs, not the clarified P08 intent.

## 3. Specification impact

- **Amends/supersedes P05 (005) for the affected case:** changes sample-row insertion count (`H-1` -> `H-2`), snapshot anchor (`P` -> `P-1`), and resulting final range/coordinate semantics. `.ai/problems/005_p05_insert_rows_template_row_spec.md`, `configuration-model.md`, and `pipeline-and-dataflow.md` must be updated accordingly.
- **No row deletion:** P08 no longer proposes deleting template boundary rows; deletion-based approach in earlier P08 draft is withdrawn by clarification.
- **Scope to confirm:** clarification was given in template-insertion context; apply to `insert_rows=TRUE` with non-blank `template` unless PO states all `insert_rows=TRUE` targets.

## 4. Targeted rework (implementation task)

**Objective:** for `insert_rows=TRUE` (assumed template-prepared sheets, OP-1), insert sample row `P` `H-2` times and paste snapshot at `(P-1, pc)` with full `H x W`, preserving snapshot data/transfer semantics (`only_values`, `skip_header` slicing already applied to `H/W`) and correct final-range handoff to formatting/grouping.

### 4.1 Proposed algorithm (to validate/encode)

Let `P = configured paste_row` (normalized input), `pc = paste_col`, `H = snapshot.Rows.Count`, `W = snapshot.Columns.Count`.
- **Precondition (recommended):** require `P >= 2` (so `P-1 >= 1`) when this mode applies; fail-fast with contextual diagnostic if not.
- **Row preparation:** if applicable, copy **entire sample row `P`** and insert it **`H-2` times** starting at `P` (Excel row-insert semantics) so original `P` and rows below shift down as in P05 mechanics but with adjusted count.
  - `H <= 1`: `H-2` is negative -> define explicit behavior (OP-2).
  - `H == 2`: insert `0` sample rows.
  - `H >= 3`: insert `H-2` sample rows.
- **Snapshot write:** paste snapshot at destination top-left **`(P-1, pc)`** over `H x W` using existing `PasteSnapshotData` / `only_values` semantics (no range shrink).
- **Final range:** recompute and return actual inserted snapshot range (expected `P-1 .. P-1+H-1` at `pc..pc+W-1`, subject to confirmed mechanics) so `ApplySheetFormatting` and `ApplyOutlineGrouping` operate on correct bounds (`modTreportRun.bas:208-211`).
- **No row deletions.**

> Implementer must verify exact row-shift/final-range math against Excel behavior during implementation (L3 on copies), especially interaction between inserting copies of row `P` starting at `P` and writing snapshot starting at `P-1`.

### 4.2 Edge cases / decisions to encode

- **`P == 1` (or `P-1 < 1`):** fail-fast with contextual diagnostic including `data_sheet`, `template` (if any), `paste_row`, `H`, `insert_rows`, operation (cannot paste at `P-1`).
- **`H == 1` or `H == 2`:** define deterministic behavior (OP-2). Options: (A) treat as valid with `max(H-2,0)` inserts and paste at `P-1` over `H`; (B) fail-fast when `H < 2` or `H < 3`. Must be explicit to avoid underflow/negative resize.
- **`insert_rows=FALSE`:** unchanged (anchor remains `P`).
- **Non-template targets:** unchanged if scope is template-only (OP-1); otherwise apply same repositioning to all `insert_rows=TRUE`.
- **`only_values` TRUE/FALSE, `skip_header`:** preserve existing transfer semantics and sliced `H/W`; only anchor/count/final-range change.
- **Template/Excel structures:** row inserts at `P` may be affected by merges/formulas/objects; fail-fast on COM errors with context.
