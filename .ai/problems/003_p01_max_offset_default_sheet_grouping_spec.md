- **Baseline context:** `/.ai/problems/001_treport_spec.md` (rev. 7 lineage), `.ai/plans/004-report-wclip-week-filter-execution.md`, current exported VBA architecture under `mko_treport/src/vbs/export/`

Final end-user runtime remains **VBA-only** in Excel; auxiliary development/deployment/inspection tools are permitted off-runtime only (per project rules).

## 1. Problem statement

Current report generation and configuration in `treport.xlsm` have three gaps affecting usability and flexibility:

1. **Default sheet in output workbooks:** generated report workbooks include an Excel-default empty sheet (created with the new workbook), so the first displayed sheet/content is not the intended report output.
2. **No offset from `max`:** where period/value maxima are used, users cannot select “previous” values relative to the maximum (e.g. last-but-one week/year). `data_files.filters` and `report_sheet` placeholders support `max`/`max_<field>` semantics but not `max - N` offsets.
3. **No row grouping by `group_rows`:** `data_files.group_rows` exists in configuration but is treated as deferred/no-op. After inserting each subreport range, rows are not grouped by Excel Outline based on the configured column/fill-color rule, reducing readability and navigation for large pasted ranges.

**Business goal:** produce cleaner, correctly ordered report workbooks; enable deterministic selection/naming of prior periods via offsets from `max`; and automatically group subreport rows per configuration so users can collapse/expand detail without manual formatting.

## 2. Confirmed requirements

### CR-1 (P01-1): Remove default sheet from generated output workbooks
- `Create_report` must not leave an Excel-default empty sheet in normally produced report workbooks. Intended report sheets/content must be the meaningful result.
- Default-sheet handling must be deterministic and must **never delete a produced report sheet**.
- Applies to all applicable report workbooks generated by the standard flow (see PO D7).
- Edge case (PO D3): if generation would yield no report/content sheet to keep, behavior must be consistent with existing fail-fast/no-data/error outcomes (do not silently produce an invalid empty workbook). Normal successful runs must never leave the Excel-default empty sheet.

**Current evidence:** output workbooks created with `Application.Workbooks.Add(xlWBATWorksheet)` (e.g. `modTreportRun.Create_report`, `modTreportOutput.GetOrCreateOutputWorkbook`); `modTreportOutput.CleanupDefaultSheets` is a no-op and not invoked; report sheets added via `modTreportOutput.AddReportSheet`. (Research: `mko_treport/src/vbs/export/modTreportRun.bas`, `modTreportOutput.bas`.)

### CR-2 (P01-2): `max - N` offset support in `data_files.filters`
- Extend `max` usage in filter expressions to support offset form **`max - N`** wherever `max` is a valid bound/value token today, including range/scalar contexts (examples: `Week Number=(1-max-1)`, `Week Number=(1-max-3)`, `Year=max-1`).
- **`max_value`:** the resolved maximum of the **referenced field** (same field named in the clause), consistent with existing per-referenced-field max resolution/domain semantics for `data_files.filters`.
- **Validity (PO D1):** `N` is an integer `>= 0`. Require `0 <= N < max_value`. `N == 0` means same as `max`. If `N >= max_value` → **fail fast with error** (clear context).
- **Domain presence (PO D2):** if `max - N` is arithmetically valid by CR-2 validity rules but the computed exact value is **not present** among the field’s values/domain items, → **fail fast** with clear context (field, resolved max, N, computed value).
- Parsing/validation must be deterministic and must not break existing valid filter expressions; malformed/unresolvable offset forms must fail fast with clear context (consistent with filter error policy).

**Current evidence:** `modTreportFilters.ParseAndClassify/ClassifyExpr`, bound tokens `min|max`/numeric (`IsMinMaxToken/IsBoundToken/CountValidRangeSplits`), per-field numeric domain/max in `ResolveFilterContext/GetOrCreateFieldState/ResolveGlobalBound`, selection via `modTreportPivot.ApplyFieldSelection`; `-` currently acts as range separator for valid bound tokens, so `max-N` is not representable today. (Research: `mko_treport/src/vbs/export/modTreportFilters.bas`, `modTreportPivot.bas`.)

### CR-3 (P01-2): `max-N_<field>` offset support in `report_sheet` placeholders
- Extend `report_sheet` placeholder model to support offset form **`<max-N_<PivotTable field name>>`** (example intent: `max-1_<field>` / `<max-1_Year>` per naming context) in addition to existing `<max_<PivotTable field name>>`.
- Substituted value is derived from the **maximum numeric value** of the named PivotTable field in the relevant pivot/data context for the processed `data_files` row, then applying offset `N` per the same validity/domain rules: `N` integer `>= 0`, `0 <= N < max_value`, `N==0` same as `max`; if `N >= max_value` → fail fast; if computed value not present among field values/domain items → fail fast with clear context (PO D1, D2).
- Placeholder resolution remains **independent of `data_files.filters`** clause derivation/representatives and independent of filter application/selection effects (consistent with existing rev.7 placeholder principle).
- Placeholder substitution applies to `report_sheet` only (existing scope). Existing naming/sanitization/31-char/collision/Trim rules remain in force after substitution.

**Current evidence:** `<max_<field>>` discovery/validation in `modTreportOutput.CollectMaxPlaceholderFields/SubstituteReportSheetPlaceholders`; row-scoped pre-filter resolution in `modTreportRun.ResolveReportSheetPlaceholderMaxValues`; numeric max/domain from `modTreportPivot.GetPivotFieldNumericMaxValue` / item domain. Legacy fixed tokens rejected. (Research: `mko_treport/src/vbs/export/modTreportOutput.bas`, `modTreportRun.bas`, `modTreportPivot.bas`.)

### CR-4 (P01-3): Automatic Excel row grouping per `group_rows` after each subreport insertion
- After inserting each subreport (`data_files` row) into the target sheet, perform grouping **within that inserted subreport range only**.
- **Subreport range bounds:** determined by insertion position and inserted range size (`paste_row`, `paste_col`, inserted `width`, inserted `height` as the pasted/presented range dimensions for that subreport). Grouping must not affect rows/cols outside these bounds and must not merge groups across different subreports.
- **Checked column:** `paste_col + group_rows - 1`, where `group_rows` is **1-based index within the inserted range**.
- **Groupable rows:** rows whose inspected cell has **no fill/pattern-none** OR an **explicit solid white fill (RGB 255,255,255)**. Any other fill/pattern/color is a **non-groupable boundary** and must not be included in a group. Conditional formatting colors are ignored (PO D5).
- **Grouping behavior:** group **consecutive** groupable rows only (standard Excel Outline / `Rows.Group`, collapsible/expandable). A non-groupable (colored/other) row ends the current group and is excluded; next group may start at next groupable row. Runs at the start or end of the inserted range must be closed/grouped correctly. A **single-row** groupable sequence is grouped as a separate group.
- **Invalid/missing/out-of-range `group_rows`:** if `group_rows` is not set, not a valid number, or `> width` (outside inserted range), **do not perform grouping** for that subreport and **do not abort the whole process** (PO D6, silent skip for that subreport).
- **Independence:** process each subreport independently (including adjacent subreports).

**Current evidence:** `TreportDataFile.GroupRows` read if column exists (`modTreportConfig.ReadConfig`) but ignored at runtime (`modTreportRun.ProcessDataFile` D13 no-op); paste via `modTreportExtract.CopyPivotSnapshot`/`ApplySheetFormatting` at `paste_row/paste_col`; inserted size derivable from presented pivot range. (Research: `modTreportConfig.bas`, `modTreportRun.bas`, `modTreportExtract.bas`.)

### CR-5 (PO-directed readiness): `rows_collapsed` setting in `general`
- Add support/readiness for **`rows_collapsed`** in the **`general`** settings table (Boolean-like `True|False`) to control default collapsed/expanded state of row groups created by CR-4.
- **Default behavior now (PO D4):** groups **expanded** by default on open. Therefore, effective default when `rows_collapsed` is `False` or not provided/blank (per implementation/defaulting rule to be made explicit and backward-compatible) must result in **expanded** groups.
- **Future-ready behavior:** when `rows_collapsed` is `True`, created groups should be **collapsed** by default. This is a configuration/readiness requirement included now so future enablement is straightforward; acceptance for this spec requires the setting to be recognized without breaking existing configs and the default-expanded outcome preserved.
- **Config compatibility:** existing workbooks/configs without `rows_collapsed` must continue to work with default-expanded behavior (no breaking change).

### CR-6: Scope, determinism, and non-regression
- P01 changes apply generally to all applicable `Create_report`/configuration cases (PO D7), not limited to a single report or `data_files` row.
- Existing valid behavior for filters, placeholders, sheet/workbook naming, output ordering, formatting, and fail-fast diagnostics must be preserved except where P01 explicitly changes it.
- All VBA changes must be made in export sources; verification follows project VBA workflow (backup/working copy, L1 build report, L2 manual VBE Compile required to claim compilation, L3 on copies when behavior changes).

## 5. Research summary

### 5.1 Current architecture (evidence-backed)
- **Config/schema:** `modTreportConfig.ReadConfig` loads `general/reports/data_files` (`input_path,output_path,delimeter`, report rows, per-`data_files` `filters/report_sheet/paste_row/paste_col/freeze_row/freeze_col/zoom/group_rows` if present). `group_rows` stored but not validated for grouping semantics. (`mko_treport/src/vbs/export/modTreportConfig.bas`)
- **Filter DSL/max resolution:** `modTreportFilters` parses clauses (`|`, `<field>=<expr>`), classifies scalar/range/list, treats `min|max` and numeric literals as bound tokens, resolves per-field numeric domain/max from pivot item values, applies selections in declared order via `modTreportPivot.ApplyFieldSelection` (field-scoped, uniform match/fail behavior). No `max-N` offset parsing today. (`modTreportFilters.bas`, `modTreportPivot.bas`)
- **Placeholders:** `modTreportRun.ProcessDataFile` resolves row-scoped `<max_<field>>` values **before** applying `data_files.filters`; `modTreportOutput` discovers/validates/substitutes tokens and rejects legacy/unresolved/placeholder-like remnants; numeric max from pivot field item domain. (`modTreportRun.bas`, `modTreportOutput.bas`, `modTreportPivot.bas`)
- **Output creation/paste:** one output workbook per report created with `xlWBATWorksheet`; sheets added/replaced by name per insertion; snapshot copied from presented pivot range (`TableRange1`/`TableRange2`) with values/formats/widths/row heights and then formatted (freeze/zoom/gridlines). Default-sheet cleanup helper exists but is stub/unused. (`modTreportRun.bas`, `modTreportOutput.bas`, `modTreportExtract.bas`)
- **`group_rows`:** explicitly deferred/no-op in run flow and docs. (`modTreportRun.bas`, `docs/01-vba-reporting/configuration-model.md`, `pipeline-and-dataflow.md`)

### 5.2 Feasible approaches and preferred options

| P01 item | Options considered | Preferred option & rationale |
|---|---|---|
| 1. Default sheet removal | (A) Workbook-scoped cleanup at defined point (end of per-report assembly, before save) removing only non-report/default/unused sheet(s) with count/identity guards; (B) manipulate global `SheetsInNewWorkbook` around creation with strict restore; (C) ad-hoc name heuristic only. | **A.** Deterministic, localized, avoids global Excel state side effects, and fits existing per-output lifecycle; must be implemented with robust guards so produced report sheets are never removed. |
| 2a. `max-N` in filters | (A) Structured parse/resolve of offset bound (base `min|max` with optional integer offset, e.g. `-N`) integrated into token/range/bound resolution and domain checks; (B) string pre-replacement; (C) generic expression engine. | **A.** Preserves determinism/diagnostics, reuses existing per-field domain/max, and makes Q1/Q2 validation explicit; requires careful disambiguation of range separator vs minus. |
| 2b. `max-N_<field>` placeholders | (A) Generalized placeholder grammar/parsing `<max(-N)?_<field>>` resolved from named field max with same validity/domain rules, independent of filters; (B) unrelated token family. | **A.** Consistent with current placeholder model and PO decisions; keeps fail-fast validation and independence guarantees. |
| 3. Row grouping | (A) Post-paste, range-scoped VBA pass in inspected column: detect contiguous groupable cells (no-fill or solid white RGB) and `Rows(...).Group` per run within subreport bounds; (B) derive groups from source semantics/labels; (C) helper markers/CF-driven approach. | **A.** Directly matches P01 rule (fill/color-based), uses standard Outline, and can be safely bounded to inserted subreport; requires precise fill detection and silent-skip on invalid params. |

## 6. Assumptions

- **A-1:** `max_value` for offsets is the same “resolved maximum of the referenced field” already used conceptually for `max` in that context (per-field numeric/domain max), ensuring consistency between `max` and `max-N`.
- **A-2:** Offset syntax accepted in filters/placeholders will be unambiguous and documented (e.g. `max-1`, `max - 1` handling per Trim/parse rules; placeholder token form aligned to existing `<max_...>` style such as `<max-1_Field>`), and must preserve existing valid tokens/expressions.
- **A-3:** `rows_collapsed` in `general` is treated as an optional boolean setting: absent/blank/`False` → expanded (default per PO D4); `True` → collapsed. Parsing is case-insensitive for `True/False` text values consistent with project `Trim`/normalization practices. (Backward compatibility required.)
- **A-4:** Inserted subreport dimensions for grouping bounds are taken from the actual pasted/presented range size at runtime (authoritative), even if `width/height` are not separately stored in config today.
- **A-5:** Excel Outline row grouping (`Rows.Group`) is the required mechanism; groups are created within the target worksheet context used for output and must not alter data values.

## 7. Constraints

- **Runtime:** final `Refresh_data`/`Create_report` behavior remains VBA-only in Excel; no external runtime dependencies introduced.
- **Source/change discipline:** edit VBA export sources (`mko_treport/src/vbs/export/*.bas,*.cls`) as appropriate; do not modify canonical workbooks blindly. Use backup/working copies for verification.
- **Verification policy:** L1 build/sync report required when VBA exports change; **L2 manual `Debug → Compile VBAProject` in Excel is required to claim compilation**; L3 functional checks on copies only when logic/run behavior changes. Report results per project rules.
- **Determinism & safety:** fail-fast with clear context for invalid/unresolvable filter or placeholder offsets/values per CR-2/CR-3/D1/D2; silent skip (no abort) only for invalid/missing/out-of-width `group_rows` per CR-4/D6. Do not introduce scope creep (e.g. new filter grammar beyond `max-N` offset need stated in P01).
- **Layout/independence:** grouping must respect subreport bounds and not merge across subreports; preserve existing PivotTable/layout/filter placement contracts except where unrelated.

## 8. Risks

| Risk | Impact | Mitigation |
|---|---|---|
| Parser ambiguity (`-` as range separator vs offset minus) | Incorrect parsing or regressions in existing ranges | Structured bound parsing with explicit precedence/validation, regression cases for existing `(1-max)`, `(min-max)`, numeric ranges, and new `max-N` forms. |
| “max_value”/domain interpretation edge cases (numeric types, duplicates, missing computed value) | Unexpected failures or wrong offsets | Apply PO D1/D2 strictly (resolved field max, integer N bounds, fail if computed value not in domain items); document and test representative field types. |
| Default-sheet removal deletes wrong sheet or violates Excel min-sheet rules | Data loss in output or runtime error | Workbook-scoped identity/guard logic (track produced sheets), never delete produced report sheets, ensure workbook remains valid; verify on working copies. |
| Fill-color detection variance (no-fill vs theme/white representations) | Over/under grouping vs business expectation | Implement PO D5 rule precisely (pattern-none or solid white RGB 255,255,255), ignore conditional formatting; validate against real styled samples in L3. |
| Outline/grouping interactions (existing outline levels, repeated runs, COM errors) | Grouping errors or broken UX | Apply per contiguous run within strict bounds, qualify ranges to target sheet, keep silent-skip policy for invalid params and consider localized non-fatal handling for grouping runtime issues if consistent with “no abort” intent; verify in Excel. |
| Config compatibility for new `general.rows_collapsed` | Break existing configs | Treat as optional with backward-compatible default-expanded behavior. |
| Hidden environment/build constraints (VBOM trust, L2 unavailable in automation) | Cannot claim compile/functional proof from automation alone | Follow project VBA workflow and report L1/L2/L3 status accurately with evidence paths. |

## 9. Open questions (non-blocking / implementation-time clarifications)

- **OQ-1 (syntax canonicalization):** Exact accepted textual forms for offsets in filters (spacing around `-`, e.g. `max-1` vs `max - 1`) and placeholder token spelling/casing for `<max-N_<field>>` should be finalized to match parser/Trim rules and documented with examples; must remain deterministic and unambiguous.
- **OQ-2 (result formatting):** Formatting of substituted offset placeholder values (integer vs decimal text) should follow existing numeric formatting/coercion behavior used for `<max_<field>>` to avoid naming regressions.
- **OQ-3 (L3 evidence scope):** Specific workbooks/data rows/sheets to be used for functional proof of each P01 item must be selected on **working copies** during implementation/verification (original data must not be corrupted).

No open **business** questions remain; PO decisions D1–D7 are recorded in §4.

## 10. Out of scope

- Any change to `data_files.filters` grammar/semantics unrelated to `max-N` offsets (P01 does not request new operators/functions beyond this).
- Deriving placeholders from `data_files.filters` or altering placeholder independence model.
- Grouping based on criteria other than `group_rows` column fill/no-fill rule defined in P01 (e.g. values, conditional formatting colors, semantic labels) unless explicitly requested later.
- Changing grouping initial state default from **expanded** except via the provided `rows_collapsed` configuration when set.
- Non-Excel runtimes, UI redesign, source data/pipeline/model changes, or unrelated refactoring/architecture redesign.
- Committing large `data/theiss` binaries/results or running verification on production/original data.
